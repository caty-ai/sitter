## เคยเจอเรื่องแบบนี้ไหม?

ถ้ามีสักข้อเดียวที่ตรงกับคุณ sitter ก็เหมาะกับคุณ

- งานที่คุณขอให้ AI ทำมันหยุดไปแล้ว แต่คุณเพิ่งรู้ตัวอีกทีหลายชั่วโมงต่อมา
- คุณส่งคำถามไป ไม่มีคำตอบกลับมา แล้วคุณก็ลืมไปเลยว่ากำลังรอคำตอบอยู่
- งานที่รันข้ามคืนดูเหมือนปกติดี แต่ถึงเช้ามันไม่ขยับไปไหนเลยแม้แต่นิดเดียว
- มีอะไรรันอยู่มากมายจนบอกไม่ได้ว่าอันไหนยังมีชีวิตอยู่บ้าง

สาเหตุเป็นอย่างเดียวกันเสมอ: **ไม่มีใครเฝ้าดู**
sitter รับหน้าที่นั้นไปทั้งหมด

มีอย่างหนึ่งที่ควรรู้ไว้ก่อน: sitter เฝ้าดู**งานที่คุณรันใน terminal** ถ้าคุณใช้แต่แอป ChatGPT หรือ Claude มันไม่ใช่สำหรับคุณ

## sitter ทำอะไรให้คุณบ้าง

สี่อย่าง ตามลำดับนี้

```mermaid
flowchart LR
    A["1. มอบหมายงาน<br/>ส่งงานของคุณให้ sitter"] --> B["2. เฝ้าดู<br/>รู้ทันทีที่งานหยุดนิ่ง"]
    B --> C["3. จดบันทึก<br/>เขียนทุกอย่างลงสมุดเล่มเดียว"]
    C --> D["4. บอกคุณ<br/>ติดต่อเฉพาะตอนที่สำคัญ"]
```

- 👀 **เฝ้าดู**

  มันอยู่กับงานนั้นและคอยตรวจสอบตลอดว่างานเสร็จแล้วหรือค้างไปกลางทาง

- 📝 **จดบันทึก**

  ทุกอย่างที่เกิดขึ้น — เริ่มทำ ล้มเหลว สำเร็จ — จะถูกเขียนลงสมุดเล่มเดียว มันเป็นไฟล์ข้อความธรรมดา คุณจึงย้อนกลับไปดูได้เสมอว่าเกิดอะไรขึ้นบ้าง

- 🔔 **บอกคุณ**

  เมื่อเกิดอะไรขึ้นที่มนุษย์ควรรู้ มันจะติดต่อคุณผ่านช่องทางที่คุณเลือก ค่าเริ่มต้นคือเขียนบรรทัดหนึ่งต่อท้ายไฟล์ memo ถ้าอยากได้ข้อความ Slack หรือการแจ้งเตือนบนหน้าจอแทน ก็แค่บอกมัน

- ⏰ **ตามคำตอบ**

  มันป้องกันไม่ให้คุณถามใครบางคนไปแล้วลืมเรื่องนั้นไปเลย เมื่อเลยกำหนดเวลา มันจะเตือนคุณโดยอัตโนมัติ และสุดท้ายมันจะบอกว่า "ตอนนี้ต้องให้มนุษย์จัดการแล้ว"

## สิ่งที่คุณต้องมี

ไม่ต้องซื้ออะไรใหม่ แค่สามอย่างนี้

- **คอมพิวเตอร์**

  Mac, Linux หรือ Windows (WSL) เครื่องที่คุณใช้ทุกวันก็ใช้ได้

- **งานที่คุณรันจาก terminal**

  sitter เฝ้าดูงานที่คุณเริ่มจาก terminal AI agent อย่าง Claude Code และ Codex CLI, การเทสต์, การ build, การประมวลผลข้อมูล — **อะไรก็ตามที่สั่งรันด้วยคำสั่งได้** ใช้ได้ทั้งหมด ถ้าคุณใช้แต่แอป ChatGPT หรือ Claude มันไม่ใช่สำหรับคุณ

- **สิ่งที่ต้องติดตั้งเพิ่มและค่าใช้จ่าย**

  ไม่มี ไม่ต้องติดตั้งซอฟต์แวร์เพิ่ม ไม่ต้องสมัครบัญชี (ค่าใช้จ่ายของเครื่องมือที่ถูกเฝ้าดู — เช่น Claude Code — เป็นเรื่องแยกกัน)

ดูตารางฉบับเต็มได้ที่ [สภาพแวดล้อมที่รองรับ](docs/engineering.md#compatibility) (ภาษาอังกฤษ)

## เริ่มต้นใช้งาน

มีสองทางเข้า ถ้าคุณใช้ **AI agent ที่รันใน terminal** (Claude Code, Codex CLI และอื่น ๆ ในลักษณะเดียวกัน) การขอให้มันติดตั้งให้เป็นวิธีที่เร็วที่สุด

> **หมายเหตุ:** Claude Code ในที่นี้หมายถึงเครื่องมือสำหรับนักพัฒนาที่รันใน terminal ไม่ใช่แอป Claude ถ้าคุณมีแต่แอป ให้ข้ามไปที่ "ติดตั้งด้วยตัวเอง" ด้านล่าง

### ให้ AI ของคุณติดตั้งให้

ส่ง URL ของหน้านี้ให้ AI agent ของคุณ แล้วขอแบบนี้:

```text
https://github.com/caty-ai/sitter
ติดตั้งด้วยคำสั่ง npm install -g @caty-ai/sitter แล้วสอนวิธีใช้ด้วย
(ถ้าไม่มี npm ให้ทำตามขั้นตอนติดตั้งใน README แทน)
```

การระบุคำสั่งให้ชัดเจนช่วยไม่ให้ agent คิดค้นวิธีติดตั้งเอง: สิ่งที่ถูกติดตั้งคือแพ็กเกจ npm ทางการเพียงตัวเดียวที่เผยแพร่พร้อมหลักฐานที่มา (provenance) และใช้ `npm update -g @caty-ai/sitter` เพื่ออัปเดตให้ล่าสุดได้ ถ้าไม่สำเร็จ ก็ทำตามขั้นตอนด้านล่างด้วยตัวเอง

### ติดตั้งด้วยตัวเอง

สามขั้นตอน เปิด terminal ก่อน — บน Mac อยู่ที่ Applications → Utilities → Terminal บน Windows ให้อ่าน [การรองรับ Windows](docs/engineering.md#windows-support) (ภาษาอังกฤษ) ก่อน คัดลอกคำสั่งแต่ละบรรทัด วางลงไป แล้วกด Enter

ข้างใน sitter มีสคริปต์ข้อความที่อ่านได้เพียงไฟล์เดียว มันไม่เคยขอรหัสผ่านผู้ดูแลระบบของคุณ และไม่เคยเปลี่ยนการตั้งค่าระบบของคุณ

**ทางลัด (ถ้าคุณมี Node.js)**

```sh
npm install -g @caty-ai/sitter
```

ถ้าคำสั่งนี้จบโดยไม่มี error ให้ข้ามไปขั้นตอนที่ 2 ได้เลย มันติดตั้งสคริปต์ตัวเดียวกัน และ `npm update -g @caty-ai/sitter` ช่วยให้เป็นเวอร์ชันล่าสุดเสมอ ไม่มี `npm`? ใช้สามขั้นตอนด้านล่าง

**1. ดาวน์โหลด**

```sh
mkdir -p ~/.local/bin
curl -fsSL https://raw.githubusercontent.com/caty-ai/sitter/main/sitter -o ~/.local/bin/sitter
chmod +x ~/.local/bin/sitter
export PATH="$HOME/.local/bin:$PATH"
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc    # zsh — ค่าเริ่มต้นของ macOS
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc   # bash — ค่าเริ่มต้นของ Linux และ WSL2
```

สามบรรทัดสุดท้ายทำให้คุณเรียกเครื่องมือได้ด้วยการพิมพ์ `sitter`: บรรทัด `export` ใช้กับ terminal ที่เปิดอยู่ ส่วนสองบรรทัด `echo` ทำให้มีผลกับทุก terminal หลังจากนั้น — บรรทัดหนึ่งสำหรับ zsh (ค่าเริ่มต้นของ Mac) อีกบรรทัดสำหรับ bash (ค่าเริ่มต้นของ Linux และ WSL2) วางทั้งสองบรรทัดได้โดยไม่มีอันตราย บรรทัดของ shell ที่คุณไม่ได้ใช้ก็แค่ไม่ถูกอ่านเท่านั้น

**2. ตรวจว่ามันทำงาน**

```sh
sitter run --ledger /tmp/sitter-test.jsonl --on-fail 'cat >&2' -- sh -c 'sleep 3; echo test'
grep -o '"status":"success"' /tmp/sitter-test.jsonl
```

รอประมาณสามวินาที; ถ้าเห็น `"status":"success"` แสดงว่าติดตั้งสำเร็จแล้ว มันแปลว่า "งานถูกเฝ้าดู และการเสร็จสิ้นถูกบันทึกไว้"

สิ่งหนึ่งที่ทำให้หลายคนแปลกใจ: sitter เก็บเอาต์พุตหน้าจอของงานที่ถูกเฝ้าดูไว้ใน `~/.sitter/logs/` แทนที่จะเป็น terminal ของคุณ ความเงียบจึงเป็นเรื่องปกติ ถ้าอยากอ่าน ให้ดูรายชื่อไฟล์ด้วย `ls ~/.sitter/logs/` แล้วเปิดไฟล์สักไฟล์ด้วย `cat ~/.sitter/logs/<filename>`

**3. ให้มันเฝ้างานของคุณเอง**

```sh
sitter run --ledger ~/.sitter/runs.jsonl --on-fail 'cat >> ~/sitter-alerts.txt' -- sh -c 'sleep 30; echo done'
```

แทนที่ทุกอย่างหลัง `--` ด้วย**คำสั่งที่คุณพิมพ์อยู่เป็นปกติ** ทุกครั้งที่งานนั้นล้มเหลวหรือค้าง จะมีบันทึกต่อท้ายลงใน `~/sitter-alerts.txt` ประวัติของสิ่งที่เกิดขึ้นจะอยู่ใน `~/.sitter/runs.jsonl` (ทั้งสองเป็นรูปแบบที่เครื่องอ่านได้ แต่ละบรรทัดจึงดูเหมือนข้อความยาว ๆ หนึ่งบรรทัด)

ตัวอย่างนี้แค่**เขียนลงไฟล์** — ไม่มีอะไรเด้งขึ้นบนหน้าจอ ถ้าอยากได้การแจ้งเตือนบนเดสก์ท็อปหรือข้อความ Slack แทน ให้เปลี่ยนสิ่งที่ `--on-fail` รัน ถ้าไม่แน่ใจว่าทำอย่างไร ให้ถาม AI agent ของคุณว่า "ขอการแจ้งเตือนของ sitter ที่แสดงในศูนย์แจ้งเตือนของ macOS" — หรือบน Linux และ WSL2 ให้ถามว่า "ขอการแจ้งเตือนของ sitter ผ่าน `notify-send`" (บน WSL2 ที่ไม่มีเดสก์ท็อป Linux ให้ขอ Windows toast แทน เช่นผ่าน BurntToast ของ PowerShell)

**เข้าใจว่าอะไรนับว่า "ค้าง"**

sitter ถือว่างานค้างเมื่อมัน**ไม่ผลิตเอาต์พุตเลย — ทั้งบนหน้าจอและใน log — เป็นเวลา 15 นาที** และมันจะหยุดงานนั้น (โดยมีขีดจำกัดเวลาสูงสุดสี่ชั่วโมง) ถ้าคุณกำลังเฝ้างานที่เงียบจนกว่าจะเสร็จ ให้บอก sitter ให้ใช้เฉพาะขีดจำกัดเวลา ความหมายที่แน่นอนของฟิลด์ใน ledger และค่าของ hook สำหรับผลลัพธ์เหล่านี้กำหนดไว้ใน [ledger reason contract](docs/reference.md#ledger-reason-contract-run-family)

```sh
sitter run --ledger ~/.sitter/runs.jsonl --on-fail 'cat >> ~/sitter-alerts.txt' --stall-after 0 --timeout 3600 -- sh -c 'sleep 30; echo done'
```

ถ้างานเงียบแต่ wrapper ตรวจยืนยันได้ด้วยต้นทุนต่ำว่างานยังปกติ ให้คงการป้องกันงานค้างไว้ด้วย `--heartbeat-file` ใช้ไฟล์ heartbeat แยกหนึ่งไฟล์ต่อ run ที่เฝ้าดู ห้ามใช้ร่วมกันระหว่างหลาย run และให้ wrapper touch ไฟล์อย่างน้อยถี่เป็นสองเท่าของ `--stall-after` (mtime มีความละเอียดเป็นวินาที และ sitter ตรวจทุก 15 วินาที) ภายใน wrapper ให้ worker เป็นโปรเซสเดียว (เรียกด้วย `exec`) หรือส่งต่อ `TERM` ไปยังโปรเซสลูก มิฉะนั้นเส้นทาง kill ของ wrapper เองจะปล่อยให้โปรเซสหลานยังทำงานอยู่

```sh
sitter run --ledger ~/.sitter/runs.jsonl --on-fail 'cat >> ~/sitter-alerts.txt' --heartbeat-file ~/.sitter/heartbeats/quiet-worker --stall-after 900 --timeout 3600 -- ./examples/heartbeat-wrapper.sh
```

| สถานการณ์ | วิธีใช้ |
| --- | --- |
| งานมีเอาต์พุตตามปกติ แต่บางครั้งเงียบนาน | เพิ่มค่า `--stall-after` |
| งานเงียบจนเสร็จ และไม่มีสิ่งใดยืนยันสถานะได้ระหว่างทาง | `--stall-after 0 --timeout <ขีดจำกัด>` |
| งานเงียบ แต่มีสิ่งที่ตรวจยืนยันสถานะได้ด้วยต้นทุนต่ำ | ใช้ wrapper กับ `--heartbeat-file` และคงทั้ง `--stall-after` กับ `--timeout` |

<summary>ถ้ามีอะไรผิดพลาด</summary>

<br>

**ขึ้นว่า `sitter: command not found`**

สามบรรทัดสุดท้ายของขั้นตอนที่ 1 อาจยังไม่มีผล รันบรรทัดนี้บรรทัดเดียว แล้วลองอีกครั้ง

```sh
export PATH="$HOME/.local/bin:$PATH"
```

ถ้ายังเป็นอยู่ ให้ปิด terminal แล้วเปิดใหม่

**การดาวน์โหลดขึ้น `404`**

ช่วงที่เพิ่งปล่อยเวอร์ชันใหม่ อาจต้องใช้เวลาสักครู่กว่าจะกระจายทั่ว รอสักครู่แล้วรันอีกครั้ง

## ทำไมจึงใช้ได้อย่างปลอดภัย

"ไม่ลงมือทำอะไรเองเด็ดขาด" คือเสาหลักที่ sitter ถูกออกแบบขึ้นมา

- **มันไม่เคยลองใหม่ด้วยตัวเอง**

  งานที่ล้มเหลวจะถูกลองใหม่เฉพาะเมื่อคุณประกาศไว้อย่างชัดเจนว่าลองใหม่ได้อย่างปลอดภัยเท่านั้น นอกนั้นทั้งหมดจะถูกรายงาน ไม่ถูกทำซ้ำ

- **มีเกราะกันการพลาด**

  คำสั่งที่เผยแพร่ข้อมูลหรือเสียเงิน — เช่น `git push`, `npm publish`, `kubectl delete` — จะถูกปฏิเสธก่อนที่จะถูกเฝ้าดูด้วยซ้ำ แต่ต้องเข้าใจให้ชัดว่ามันคืออะไร: มันเป็นเพียง**เกราะกันอุบัติเหตุแบบง่าย ๆ** ไม่ใช่กำแพงกันการกระทำอันตรายทุกอย่าง (ตัวอย่างเช่น `rm` ไม่ได้ถูกครอบคลุม)

- **ทุกอย่างถูกจดไว้**

  ไม่ว่าจะเกิดอะไรขึ้น คุณย้อนติดตามมันในสมุดบันทึกได้ทุกเมื่อที่ต้องการ

- **บรรทัดเดียวหยุดทั้งหมด**

  บรรทัดเดียวนี้หยุดการเฝ้าดูและการลองใหม่ทั้งหมด

  ```sh
  touch ~/.sitter/STOP
  ```

## สถานะโปรเจกต์

[![CI](https://github.com/caty-ai/sitter/actions/workflows/ci.yml/badge.svg)](https://github.com/caty-ai/sitter/actions/workflows/ci.yml)

- **CI** — แบดจ์ด้านบนเป็นสถานะสด: ทุก push ไปยัง main และทุก pull request จะรัน fault-injection suite แบบเต็ม และจำนวนเคสถูกรายงานโดยอัตโนมัติจาก `make test`
- **สภาพแวดล้อมที่ยืนยันแล้ว** — Ubuntu เป็นเกตสำหรับทุก pull request; macOS รันทุกครั้งที่ push ไปยัง main; Windows (Git Bash) รองรับแบบพยายามเต็มที่
- **ระดับความนิ่งของโปรเจกต์** — v0.4.0; การทำงาน v0 ทั้ง 4 แบบ (`run` / `expect` / `ack` / `sweep`) ถูกตรึงสเปกไว้ใน `docs/requirements-v0.md` ส่วน `ask` / `watch` ถูกกำหนดไว้โดย `docs/specs/prd-v0.2-ask-watch.md` (ตรวจสอบแล้วใน v0.2.0)
- **ข้อจำกัดที่ทราบแล้ว** — denylist เป็นตัวกันพลาดจากอุบัติเหตุ ไม่ใช่กำแพงความปลอดภัย; จะลองใหม่เฉพาะงานที่คุณประกาศไว้ชัดเจนว่าเป็น idempotent เท่านั้น
